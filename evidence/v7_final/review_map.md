# v7 Review Map — segmented folders + read order

**Purpose.** The v7 compounding-loop artifacts are scattered across `evaluation/src/loop/`,
`evaluation/src/experiments/`, this `evidence/v7_final/` folder, and
promoted-live code under `Agents/`. This map segments **everything on, or validating, the v7 loop** into
review folders, in the order you should read them, so the review is bounded and first-principles.

**This is a MAP, not a physical move.** The code lives where it runs; I am *not* relocating it, because
(a) the loop code under `evaluation/src/` and the substrate under `Agents/` would break their imports if
moved, and (b) `evidence/` is a frozen record by policy (CLAUDE.md), not a code home. Each entry below is
a **pointer** to where the file actually is. For files already **promoted to live** under `Agents/`, the
pointer is its real location and it is marked 🔵 — those you audit in place.

**Legend.** 🔵 LIVE = promoted into `Agents/`, audit in place · ⚠ = review-priority (subtle / risky /
known-issue) · 💤 = off the default v7 path (built but disabled, or offline-only) · ★ = load-bearing,
do not skip.

## Review order (the folders, in dependency order — first principle → final outcome)

A bug in an earlier folder invalidates everything after it, so read top-down:

| # | Folder | The one question it answers | Why here |
|---|--------|------------------------------|----------|
| **0** | Design & intent | *What was the loop trying to do, and what's the trust stack?* | Orientation before any code — gives every file a "why". |
| **1** | Foundations (🔵 live) | *What is a "decision", a "faction win", a "metric"?* | The proxy reads these; if "won" is wrong, all credit is wrong. |
| **2** | Proxy & lever validation / screening | *Is the measurement (and each lever) actually legitimate?* | The trust-stack preconditions (§0–§2). The screens validate the **exact** scoring code Folder 3 runs. |
| **3** | In-loop evaluation engine | *How does the loop score decisions & assign credit each generation?* | Trust-stack §3 (credit). This is the signal the whole headline rests on. |
| **4** | Live v6 read/write substrate (🔵 live) | *How does a single game write & read memory?* | Trust-stack §1 (substrate). Runs in the game subprocess every generation; produces what Folder 3 scores. |
| **5** | Memory-mutation / consolidation | *How does the store change between generations? (the thing on trial)* | Trust-stack §4. The actual compounding mechanism. |
| **6** | Orchestration | *How are 3–5 wired into a generational A/B loop with guards?* | The control flow + the fail-closed guards that make a run trustworthy. |
| **7** | Run records & outcome | *What did the (invalid) runs show, why invalid, what does the final run measure?* | The outcome — read last, against everything above. |

⚠ **Known issue to decide on before the final run — the evict lever is wired but inert.** `consolidate`'s
evict path requires `retrieved_count >= 8` (+ override-dominance), but `retrieved_count` /
`override_count` / `not_relevant_count` are never initialized on synthesized SPs, never set by
`credit_apply`, and never merged back into the loop store — so the precondition can never be true and
`evicted=0` always. Confirmed live: every SP in `v2_full/gen6_store/strategy_points.json` shows
`"retrieved_count": 0` despite high `follow_count`s. Only **prune-by-lift**, **obs-decay**, and **synth**
actually mutate the store. Decide: wire retrieved/override through, or remove the dead lever.
