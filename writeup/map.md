# Write-up map

The working index for the portfolio write-up of the agent side (server and frontend are mapped
separately). The method is bottom-up: walk the `evidence/` tree folder by folder, collect the
building blocks each folder offers, and only when every folder is walked decide how the blocks group
into sections and what the headings are. No section structure is fixed before then.

Rules the walk follows (ruled 2026-10-13 and 2026-10-14):

- The write-up is the page content, drafted here and ported later. It is written for a hiring reader
  who meets the project cold. All explanatory content and exhibits belong on the site; the evidence
  folder and the code are linked as supporting records, never required reading (owner 2026-10-25; the
  levels are under "Page levels" below).
- Organisation is decided at the end, from the blocks. The earlier top-down cut (sections by artifact,
  skills as hub tags) is one candidate to test against the collected blocks, not the plan.
- Evidence stays frozen. A folder that is unreadable gets a report-style pass (synthesis layer only,
  journey logs are not laundered) before it is mined, so the write-up distils from a correct record.
  A folder is also re-verified against today's code before mining; a stale report is corrected first.
- The owner walks the folders in alphabetical order of `evidence/` (ruled 2026-10-22); the tables
  below keep the README grouping. A row walked by the AI without the owner's read says so in its
  notes and is revisited when the owner reaches it.

## The model (refined as we go; agreed after `agent_boundaries/`, 2026-10-14)

A **topic** is a unit of the page. Most topics are components (the information boundary, the
scheduler, the memory store). A skill becomes a topic too when it is broad enough and no single
component owns it: cost optimisation is the first (caching, batch inference, model choice by task and
cost attribution come from four folders), and a skill tag that keeps collecting blocks across topics is
promoted the same way (agreed 2026-10-14). Every topic is told through the same five **segments**, so a
segment is a slot a block fills, never a label:

| Segment | What goes in it |
|---|---|
| Problem | Why the thing had to exist, in the game's own terms. One paragraph. |
| Design | What was built and the reasoning: the principle, the alternatives, the trade-off accepted. |
| Verification | How we know it works, and how far that knowledge reaches (what the check is blind to). |
| Case study | One concrete episode that proved the design real: a regression, a before-and-after, a number. The exhibit lives here. |
| Gaps | What is still open, stated with its consequence. Every topic has one; it is not a finding. |

A **building block** is one thing the page could say or show, filed under a topic and a segment. It
carries four fields:

- **Segment**: which of the five slots it fills.
- **Skill tags**: the specific agentic-AI skill the block demonstrates, in the field's own term
  (context isolation, invariant checks, observability, prompt caching, retrieval, ...). Tags are
  specific enough to describe the evidence. Public chapter tags are a smaller, curated set in
  `skills_inventory.md`; narrow block tags are supporting keywords, not all separate resume skills.
  A gap, a planned feature or a framework capability alone does not establish a demonstrated skill.
  "Design principle", "debugging" and "honest gaps" are not standalone capability tags. A skill that collects enough blocks across topics may earn its own
  section at the end; otherwise it stays inside the topics it appeared in. The tags are also the
  evidence behind the hub's capability tags; they are not published wholesale.
- **Exhibit form**, as in [`eval_exhibits.md`](eval_exhibits.md): **content** (prose, a number, a
  table on the page), **export** (an interactive piece fed by script-generated JSON), **link** (a
  replay on the live site or a folder or file on GitHub). A real example is always lifted from the
  record, never invented.
- **Source**: the evidence path (and the code path when the reader may want to verify).

Rules of thumb that came out of the first folder:
- A table of internals (eleven check names) means nothing to a stranger; a paragraph with one real
  line from the log and a link to the code does more. Tables are for things a reader compares.
- A number goes on the page with its caveat in the same sentence ("109 flags, none rendered").
- When a block's real reason lives in another topic (the public-by-design fields exist to cut
  hallucination), it is filed there, and the first topic keeps a one-line cross-reference. Parked
  cross-references are listed below so they are not lost.
- Terms: the owner tags in plain words; the ledger records the field's term next to it the first
  time (information boundary = context isolation; leak test = invariant checks over a post-hoc
  transcript audit; the capture point = observability; a prompt segment included only when the
  seat can act on it = conditional prompt composition, a sibling of isolation under context
  engineering: isolation is about what the agent may not know, composition about what it cannot use;
  the call that produces something never grades it = generator-verifier separation; a judge that
  counts without seeing the labels = blind annotation; a post-generation check with code deciding =
  output guardrail).

### Page levels (owner 2026-10-25; every chapter)

Each chapter has a Level 1 page that introduces the topic and summarises its main findings and
decisions. Level 2 pages develop substantial subjects into complete, readable explanations. Level 3
pages are optional, reserved for specific investigations or technical details that merit deeper
exploration. All explanatory content and exhibits belong on the portfolio; repository links provide
supporting records and code. A reader can follow the whole engineering story without leaving the site.

| Level | What earns a place | Evaluation example |
|---|---|---|
| 1: Chapter | The overall approach and representative findings | Evaluating the agents and the systems around them |
| 2: Substantial subject | A question requiring several connected explanations, decisions or examples | Designing and validating LLM judges |
| 3: Specific investigation | One case whose setup, analysis or implications warrant additional detail | Why a quality rubric gave nearly every output the same high score (`evaluation/llm_judge/report.md`, case 5) |
| Evidence link | The original artifact supporting a claim | Prompt, run outputs, analysis script or experiment record |

- **Content decides the structure, not the folders or a section count.** A report becomes a Level 2
  subject when it holds a substantial engineering story of its own; a short report with one useful
  finding becomes a subsection of another page. A broad subject splits into several Level 2 pages whose
  summaries sit together on Level 1. A chapter's first outline is a starting arrangement, not a limit.
- **Exhibits sit inside the explanation**, at whichever level they help, where the reader needs them. A
  Level 3 page reads as a coherent story, not an appendix of artifacts.
- **Assigning pages:** list each report's strongest reader-facing questions, then decide which deserve
  Level 2 pages, which combine, and which hold an investigation worth a Level 3 page.
- **The levels are depth, not order.** The project case-study page sits above the chapters. A chapter's
  narrative order (such as Memory's iterations) is independent of this depth structure. No empty pages
  just to fill all three levels.

### Topic: factual errors, measuring and containing them (skill topic, provisional, opened 2026-10-22 as "hallucination"; renamed 2026-10-23 by the owner, with hallucination as one subtopic; "how do you deal with hallucination?" is a common interview question and the project has measured answers)

factual errors" ([content plan](evaluation/content_plan.md), page 1); it is not a separate page.*

A factual error is a statement the game record contradicts: a grounding failure, where what the agent
says no longer matches the true state of the game. The project measured the symptom; causes were
diagnosed case by case (`evidence/evaluation/factual_errors/report.md`, "What counts as a factual
error"). Subtopics, one per cause:
- **Hallucination (fabrication):** invented vote records and attacks, invented own actions (the
  investigator's check), invented claims repeated by other players, claim misattribution.
- **Reasoning failures:** miscounting who is left (the largest census class, 221 of 368), invalid
  inferences. Cross-reference: the deduction topic's Problem block (48) is this cause.
- **Misreading correct information:** a visit read the wrong way round, an empty watch read as an empty
  house.
- **Losing track of state:** a dead player treated as alive, a dead player's role misstated.
- **Missing or confusing input:** the code audit's findings (the healer had no record of its own
  protections; engine facts rendered like summaries).

How each cause was found and reduced, with sources: `evidence/evaluation/factual_errors/report.md`, step 3
(the cause table) and step 4. What was tried against the errors and what worked (telling the model did not;
giving it the fact or moving the check into code did): `evidence/gameplay/report.md`, problem 1
(2026-10-24).

**Decided (owner 2026-10-22): the memory section opens with the problem, then tells the iterations.**
- Open with the problem, not the idea: agents in a hidden-role game make the same mistakes every game;
  a person would learn from the last one; can an agent? Memory then arrives as the answer tried.
- Each iteration is told in four beats: the problem at that point → what we tried → how we found out
  (the evaluation) → what it revealed (the next problem). The evaluation is not a separate chapter; it
  is how each turn of the story happened, so the instruments blocks hang off beat 3.
- The spine is the arc of `memory_system/report.md` ("the bottleneck kept moving": one
  document overfit → duplicates → retrieval precision → the content of the lessons → a self-improving
  loop, tested negative in July and diagnosed → v8 rebuilt for ten seats, live as an opt-in, not tested
  at scale). Numbers come from the primary folders, never from that doc.
- Each beat draws its blocks from the topics in time order (Problem, Design, Verification, Case study
  and Gaps segments map onto the four beats).
- When the memory section is published, `SITE.caseStudy` in `frontend/src/lib/site.ts` (today
  `memory_system/report.md` on GitHub) points at it.

**How the hooks are used (owner 2026-10-25).** The reader has no expectation of the game's cost or how it
plays, so a hook never argues ("why is it so cheap?") and never holds its answer: it is the question a
curious newcomer asks next, in the order they would ask it, with the answer as the first line under it.
The order: what a game costs → how well the agents play → (the model choice joins the two) → onward. An
answer gives the newcomer a reference point, since a bare number means nothing to someone with no
estimate. Hook #3, worked:

> **What does a game of Werewolf with ten AI players cost?**
> About $0.21–0.26 on Claude Haiku 5.5. With Opus 5.5 in every seat, the same game would cost an estimated
> $8–10.

The Opus figure is an estimate (2026-10-25): the token counts of two ten-seat Haiku games from 2026-10-13
(current layout, memory on, every call on the seat model except one $0.0045 Gemini 3.1 Flash-Lite call
in the second game (checked 2026-10-29), 197 and 228 calls; read from their traces with
`evaluation/experiments/game_cache_share.py` over `batch_results/cache_ab_2026_10_13/haiku_after.jsonl`)
repriced at Opus 5.5's rates ($4 input, $20 output, $0.20 cache read, $5 cache write per million tokens):
$8.41 and $9.99, or $7.09 and $7.92 without the memory lookups. Output is about half the bill and would
